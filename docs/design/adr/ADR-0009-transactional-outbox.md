# ADR-0009 状態変更の後続処理はTransactional Outboxで連携する

## ステータス

Accepted（2026-08-11）

## コンテキスト

決済の状態変更（オーソリ成功、キャプチャ、返金）には後続処理（台帳記帳、通知、管理画面へのSSE配信）が伴います。状態変更のコミットと後続処理の実行を確実に両立させる必要があります。Zenn記事「Goとsunabarで送金を本番品質にする — Outbox/CircuitBreaker設計」「マイクロサービス間でのデータ連携方法」の知見を織り込みます。

## 決定

Transactional Outboxパターンを採用します。決済の状態変更とoutbox_eventsテーブルへのイベント追記を同一DBトランザクションでコミットし、リレーワーカーがSELECT FOR UPDATE SKIP LOCKEDでイベントを取り出して後続処理を実行します。処理はat-least-once前提で、消費側を冪等にします。

CDC（Change Data Capture。WALの論理レプリケーションで変更を捕捉する方式）は本決定の代替として比較検討し、第3段階の拡張候補（PostgreSQLのlogical replication + wal2jsonでOutboxリレーを置き換える学習課題）として位置づけます。

## 根拠

Outboxは追加ミドルウェアなし（PostgreSQLのみ）で二重書き込み問題を解消でき、モノリス+単一DBの本構成に適合します。CDCはDebezium等の基盤が必要でMVPの「複雑すぎない」制約に反しますが、Outboxポーリングの遅延・負荷限界を体感した後の学習ステップとして価値があります。

## 影響

outbox_eventsテーブル（イベント種別、ペイロードJSONB、状態、リトライ回数、次回実行時刻）を追加します。リレーワーカーのポーリング間隔と指数バックオフを03-basic-designで定義します。

## 検討した代替案

同期実行（状態変更と同一リクエスト内で後続処理）はPSP呼び出し失敗時に不整合を残します。メッセージキュー（Kafka等）の導入は二重書き込み問題が残るうえ運用対象が増えます。CDCは上記のとおり拡張へ回します。
