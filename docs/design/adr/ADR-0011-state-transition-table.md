# ADR-0011 決済の状態管理は状態×イベントの遷移テーブル駆動とする

## ステータス

Accepted（2026-08-11）

## コンテキスト

決済は8状態（created、authorized、captured、canceled、expired、failed、refunded、partially_refunded）を持ち、if文の分岐で管理するとフラグ地獄になります。Zenn記事「Go + Reactで現場レベルの状態遷移を1つのテーブルに統合する」の知見を織り込みます。

## 決定

許可される遷移を「現在状態×イベント→次状態」の遷移テーブル1つに定義し、テーブルにない遷移はすべてエラーとします。テーブルはGoコード内の宣言的なマップとして持ち、03-basic-designの遷移表と1対1対応させます。

## 根拠

許可遷移が1箇所に集まるため、設計文書との突き合わせとテスト（全セル網羅）が機械的にできます。不正遷移（capturedへの二重キャプチャ等）がテーブル参照の時点で拒否されます。

## 影響

状態遷移テストは遷移テーブルの全セル（許可・拒否の両方）を網羅します。状態の追加はテーブルと設計文書の同時更新を必須とします。

## 検討した代替案

各ハンドラ内のif分岐は遷移の全体像が分散して監査できません。ステートマシンライブラリ（looplab/fsm等）は依存を増やすわりに遷移テーブルの宣言以上の価値がありません。
