# ADR-0007 二重決済防止はサーバ発行の冪等性キーとDB一意制約で行う

## ステータス

Accepted（2026-08-11）

## コンテキスト

決済リクエストはネットワーク再送・多重クリック・リトライで二重実行されます。AIエージェント経由の呼び出しが同一決済を複数回叩く事例も想定します（Zenn記事「AIエージェントは同じ決済を平気で三回叩いてくる」の知見）。

## 決定

冪等性キーは自社API層が決済1件ごとに発行し、UNIQUE制約付きのidempotency_keysテーブルへ処理前にINSERTします。同一キーの同時リクエストは片方だけがINSERTに成功し、後続は保存済みの結果（未確定なら「処理中」の409）を返します。

StripeのIdempotency-Keyはエンドポイント＋パラメータの組で照合されるため、操作種別ごとに決済キーから派生キーを導出して使います。PaymentIntent作成は`{key}:create`、キャプチャは`{key}:capture`、返金は`{key}:refund:{返金連番}`とします。外部クライアント向けAPIは本プロジェクトのスコープ外のため、クライアント指定キーの受け入れは実装しません。

## 根拠

DB一意制約は競合状態でも原子性を保証する唯一の層です。派生キーをPSPへ引き継ぐことで、PSP呼び出しがタイムアウトした「請求成立が不明」な状態でも同一派生キーの再送で結果だけを取得でき、二重請求を防げます。操作種別を派生キーに含めるのは、Stripeが同一キーの異種操作を`idempotency_error`として拒否するためです。

## 影響

idempotency_keysテーブルはキー・リクエストハッシュ・応答スナップショット・有効期限を持ちます。同一キーで異なるリクエスト本文が来た場合は409を返します。期限切れキーの削除は`internal/housekeeping`の定期ジョブが行います（03-basic-designの1章・4.4節）。

## 検討した代替案

アプリ層の排他制御（mutex）のみでは多プロセス構成で破綻します。SELECT FOR UPDATEのみでは初回INSERT競合を防げません。
