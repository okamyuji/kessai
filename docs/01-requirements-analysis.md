# kessai 要件分析書

作成日 2026-08-11 ／ 版 1.0

## 1. 背景と目的

決済システムに慣れていないGoエンジニアが、日本の決済に必要な機能を一通り理解しながら実装できる学習用決済アプリケーションを作ります。単なる写経ではなく、決済ドメインの本質的な難所（二重決済防止、状態管理、外部障害への耐性、監査証跡）を、本番品質の設計パターンで体験することを目的とします。

## 2. 対象読者

- 実装者: Goの基本文法とSQLの基礎を知っているが、決済ドメインは初めてのエンジニア
- 本書群の読者: 同上。決済用語は初出時に本文で定義します

## 3. スコープ

### 3.1 対象

デモ商品1点を購入できる最小のECチェックアウトと、その決済を運用する管理画面を作ります。決済手段はクレジットカード（Stripeサンドボックス経由）のみです。

### 3.2 対象外

| 対象外 | 理由 |
|---|---|
| カード情報の自社処理 | 割賦販売法の非保持化義務とPCI DSSフル準拠の回避（ADR-0001） |
| 資金移動業・前払式支払手段 | 資金決済法上の登録が必要な領域で学習範囲外 |
| 本番PSPアカウント・実カード決済 | サンドボックスのみ（ADR-0002） |
| クラウドデプロイ | ローカルDocker Compose完結（ADR-0015） |
| 商品カタログ・在庫・配送管理 | 決済学習の本質ではないためデモ商品1点に固定 |
| マイクロサービス分割とSaga | モノリス+単一DBで適用条件を満たさない（ADR-0016） |

## 4. 機能要件のMECEロジックツリー

「決済システムの機能」を頂点に、漏れなく重複なく4系統へ分解します。葉の番号は02-requirements-specificationのFR番号と1対1対応します。

```text
決済システムの機能
├── A. 決済実行系（お金が動く瞬間の処理）
│   ├── A1. カード決済の受付（トークン化フォーム経由） ……………… MVP
│   ├── A2. 与信（オーソリ）と売上確定（キャプチャ）の分離 ………… MVP
│   ├── A3. 3Dセキュア（EMV 3-DS）による本人認証 …………………… MVP（PSP機能で有効化）
│   ├── A4. 二重決済防止（冪等性キー） ……………………………………… MVP
│   └── A5. サブスクリプション課金 …………………………………………… 拡張候補
├── B. 決済後処理系（決済の後に発生する処理）
│   ├── B1. 返金（全額・一部） ………………………………………………… MVP
│   ├── B2. Webhook受信（署名検証・冪等処理・非同期化） …………… MVP
│   ├── B3. 対帳（PSP入金明細と自社台帳の突き合わせ） ……………… 拡張候補
│   └── B4. 領収書・適格請求書（インボイス）発行 ………………………… 拡張候補
├── C. 管理・運用系（人が見て操作する部分）
│   ├── C1. 取引一覧・検索・詳細表示 ………………………………………… MVP
│   ├── C2. 返金操作画面 ………………………………………………………… MVP
│   ├── C3. Webhookイベント・Outboxイベントのログ閲覧 …………… MVP
│   └── C4. 台帳・残高の可視化 ………………………………………………… 拡張候補
└── D. 法令・セキュリティ対応系（守らないと事業ができない部分）
    ├── D1. カード番号非保持化とPCI DSS SAQ Aの維持 ……………… MVP（構成で担保）
    ├── D2. 特定商取引法の表示（最終確認画面の6項目等） ……………… MVP
    ├── D3. 管理画面の認証・認可 ……………………………………………… MVP
    ├── D4. APIキー・シークレット管理 ……………………………………… MVP
    └── D5. 監査証跡（誰がいつ何をしたかの記録） ……………………… MVP
```

決済手段の追加（コンビニ払い・PayPay等）はA1のバリエーションとして第3段階の拡張候補に置きます（3.2節のスコープ表参照）。CDCによるOutboxリレー置き換えはB2の実現方式のバリエーションとして、同じく第3段階に置きます（ADR-0009）。

## 5. 品質特性の要求（NFRの源泉）

1. 整合性を最優先します。決済と台帳の記録は1件も失わず、矛盾させません。性能より整合性を優先します。
2. 外部（Stripe）の障害が自システムの停止に波及しないこと、復旧後に自動で追いつくことを求めます。
3. すべての金銭操作に「誰が・いつ・何を」の証跡を残します。
4. 決済初心者が読めるコードと設計であること自体を品質要求とします。暗黙の前提を作りません。

## 6. 制約

| 制約 | 内容 |
|---|---|
| 技術 | Go 1.26系（ADR-0004、go.devのdl APIで実測）、PostgreSQL 18系（ADR-0003）、htmx 2系+templ（ADR-0013）、Stripeサンドボックス（ADR-0002） |
| 法令 | 割賦販売法（非保持化）、特定商取引法（表示義務）。EMV 3-DS原則導入（ガイドライン6.0版、確信度は中） |
| 運用 | ローカルDocker Compose、Stripe CLIによるWebhook転送（ADR-0015） |
| プロセス | 設計文書は`go run ./cmd/doclint docs`の緑化とN=3レビューを経て確定します |
